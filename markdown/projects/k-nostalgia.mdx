## 구현 상세

### 1. 결제 흐름 전체 설계 및 UX 이슈 대응 (대표 사례)

> 결제 플로우 및 환불 처리 구조는 요구사항 정리부터 설계, 구현까지 주도적으로 담당했습니다.

#### **문제 상황**

결제창이 켜진 채 브라우저 뒤로 가기 사용 시 결제 팝업 잔존하는 문제가 발생했습니다.  
이는 실제 사용자 테스트 과정에서 발견된 치명적인 UX 이슈였습니다.

#### **판단**

결제는 금전 이동이 발생하는 민감한 구간으로,  
예외적인 브라우저 동작까지 고려한 명확한 상태 제어가 필요했습니다.

#### **고려한 대안**

- 클라이언트 상태로 결제창 열림/닫힘을 추적하는 방식
  → 새로고침, 강제 종료 등 예외 케이스 대응 불완전

#### **선택한 방식**

- 라우팅 구조 자체를 결제 흐름에 맞게 설계 (`/payment` → `/check-payment` → `/complete-payment`)
- `popstate` 이벤트로 히스토리 변경 감지 및 결제창 제어

#### **해결**

1. 결제 전·중·후 단계를 명확히 분리한 라우팅 구조 설계
   (`/payment` > `/check-payment` > `/complete-payment`)
2. `popstate` 이벤트를 활용해 브라우저 히스토리 변경 시 결제창 종료 안내 토스트 출력
3. 결제 성공/실패에 따른 상태 분기 로직 분리

### 2. 주문 취소시 DB 상태 자동 동기화 (Webhook)

#### **문제 상황**

이 서비스는 포트원의 가결제(사전 승인) 방식을 사용합니다.  
가결제는 결제 승인 후 실제 청구 전까지 일정 시간(당일 자정)이 주어지며,  
이 기간 내 실결제 전환이 없으면 자동으로 취소됩니다.

초기에는 이 자동 취소 이벤트를 서버가 인지하지 못해  
주문 상태는 "결제 완료"로 남고 실제로는 환불된 상태가 발생했습니다.

#### **판단**

환불로 인한 결제 상태 변경은 클라이언트 요청만이 아닌  
결제사 이벤트를 기준으로 서버가 주도적으로 상태를 관리해야 한다고 판단했습니다.

#### **해결**

- 포트원 결제 취소 이벤트 웹훅 연동
- 서버 라우트에서 결제 취소 이벤트 수신 후 주문 상태 자동 업데이트
- 환불 시 사용 쿠폰 자동 복구 처리
- ngrok을 활용한 로컬 웹훅 테스트

#### **결과**

- 결제 상태와 주문 데이터의 실시간 동기화
- 수동 개입 없이 환불·쿠폰 복구가 처리되는 안정적인 결제 운영 구조 확보
- 운영 단계에서 수동 환불 처리에 대한 부담 감소

### 3. 쿠폰 시스템 구조 개선

<CldImage
  src={CLOUDINARY.K_NOSTALGIA.COUPON_FLOW}
  alt="쿠폰 흐름 gif"
  width={800}
/>

#### **문제 상황**

초기 MVP에서는 쿠폰 할인 금액을 클라이언트에서 계산하여  
결제 API에 전달하는 구조였습니다.

이는 빠른 프로토타이핑에는 유리했지만,  
클라이언트 조작 가능성과 서버-클라이언트 간 할인 금액 불일치 리스크가 존재했습니다.

#### **판단**

쿠폰은 단순 UI 편의 기능이 아닌 **결제 신뢰성과 직결되는 도메인 로직**이라고 판단했습니다.

#### **해결**

- 쿠폰을 독립적인 DB 테이블로 분리
- 할인 금액 계산을 서버(Route Handler)에서 수행하도록 구조 변경

#### **결과**

- 클라이언트 위변조 가능성 제거
- 결제/환불/쿠폰 복구 로직을 일관된 서버 기준으로 관리 가능

### 4. 배송지 관리 기능 구현 및 상태 일관성 개선

<CldImage
  src={CLOUDINARY.K_NOSTALGIA.ADDRESS_FLOW}
  alt="배송지 흐름 gif"
  width={800}
/>

#### **문제 상황**

배송지 정보가 마이페이지와 결제 페이지에 분산되어 페이지 이동 시 데이터 불일치가 발생했습니다.  
결제 과정에서 배송지 변경이 즉시 반영되지 않는 UX 문제가 존재했습니다.

#### **판단**

배송지는 결제 플로우 전반에서 참조되는 핵심 상태이므로,  
페이지 단위 상태가 아닌 전역 상태로 일관되게 관리해야 한다고 판단했습니다.

#### **해결**

- 배송지 CRUD 로직을 전역 상태(Zustand)로 분리
- 마이페이지와 결제 페이지가 동일한 상태 소스를 참조하도록 구조 통합
- 입력 검증, 선택, UI 전환을 하나의 흐름으로 관리

#### **결과**

- 페이지 이동 및 결제 과정에서 배송지 데이터 일관성 확보
- 사용자 입장에서 배송지 변경이 즉시 반영되는 안정적인 UX 제공

### 5. 공용 컴포넌트 설계 및 재사용성 확보

#### **문제 상황**

주문 내역, 리뷰 작성, 배송지 선택 등 여러 화면에서  
유사한 모달/풀스크린 UI가 반복적으로 필요했습니다.

각 화면마다 버튼 텍스트, 레이아웃, 동작이 조금씩 달라  
매번 새로 구현하면서 코드 중복이 누적되었습니다.

#### **판단**

UI 레벨에서 반복되는 패턴은 조기에 컴포넌트화하지 않으면 추후에 일관성을 유지하기 어려울것으로 판단했습니다.

#### **해결**

- 용도에 따른 매개 변수를 받아 그에 따라 변동되는 공용 UI 컴포넌트 구현
  - 데스크탑: 모달 / 모바일: 풀스크린 구조 등
- 결제 버튼, 아코디언, 라디오 그룹 등 공용 UI 컴포넌트 정리
- 연속 클릭으로 인한 이벤트 오류 방지를 위한 커스텀 훅 분리 (useThrottle)

#### **결과**

- UI 일관성 및 재사용성 확보
- 신규 기능 추가 시 UI 구현 비용 감소

## 회고

### 배운 점

- 프론트엔드에서도 도메인 로직(쿠폰, 환불)의 책임 경계를 명확히 설계하는 것이 서비스 안정성에 직결된다는 기준을 확립
- 웹훅 같은 비동기 이벤트 처리 경험으로 클라이언트-서버 협업 구조에 대한 이해도 향상
- 결제 도메인에서 예외 케이스(뒤로가기, 자동 환불)를 사전에 고려하는 설계 감각 습득

### 아쉬운 점

- 스크린 리더 등 접근성 테스트 부족
  - 결제 플로우는 장애인 사용자에게도 중요한 영역
- 에러 핸들링이 토스트 중심으로만 구현됨
  - Sentry 등 에러 모니터링 도구 연동 필요성 느낌
